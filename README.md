# DBC Afterlife

**Graduating isn't success.** DBC Afterlife checks a Meteora Dynamic Bonding Curve launch's settings
against what actually happened to thousands of real mainnet launches *after* they graduated, and ships
launch presets that the evidence supports.

- **Check any launch** — paste a token mint, DBC pool or DBC config address. The site reads the config from
  Solana mainnet in your browser and shows how launches with the same settings fared after graduation,
  with warnings for the settings that almost never survive.
- **Plan a launch** — try settings before you create a config, or call the checker from code before
  `createConfig`.
- **Use a preset** — two presets built with Meteora's SDK, validated by the SDK, and accepted by the live
  mainnet DBC program in simulation.

Three things stand out:

1. **Nearly half of all "graduations" are spam.** The curve "completes" at a threshold below 1 SOL, with
   almost no real buying. Any graduation statistic that counts them is meaningless.
2. **Most real graduates die anyway.** Ranking settings by graduation rate stops one step too early.
3. **The launchpad matters more than any single setting**, so settings are compared only within
   self-serve Meteora (`met-dbc`) launches. Within that group, three warning signs (starting fee ≤ 0.25%,
   threshold under 20 SOL, no locked liquidity) predict a dead pool in every sample we tested.

These are associations among graduated launches, not causes. See [DATA_NOTE.md](DATA_NOTE.md).

## Use it

**Website.** Open the live site, paste an address, or switch to "Plan a launch". No wallet, no keys,
nothing is sent to the chain.

**CLI.**

```bash
npm install
npx tsx check.ts 39ahtL8ynzE4amH26J29C93PA5172V3ft9UuUcqQS8fz   # token mint, DBC pool or DBC config
npx tsx check.ts presets/steady.json                            # ConfigParameters before createConfig
```

**In a launchpad**, before calling `createConfig`:

```ts
import { checkConfig } from "./checker.ts";
const evidence = await fetch("<site>/data/evidence_all.json").then((r) => r.json());
const verdict = checkConfig(configParameters, evidence);    // same shape as the SDK's ConfigParameters
if (verdict.level === "red") console.warn(verdict.headline, verdict.warnings);
```

**Presets.** `presets/steady.json` and `presets/anti-sniper.json` hold SDK `ConfigParameters` (numbers as
decimal strings). To get BN-typed parameters ready for `client.partner.createConfig`, call
`buildPreset(spec)` from `presets.ts` with a spec from `presets/specs.json`.

## How it works

```
DAMM v2 data API (all pools) ──► graduated, SOL-paired, ≥ 30 days old, DBC-capable launchpad
        │ seeded shuffle → Discovery / Holdout / Confirmation samples
        ▼
DBC data API (mint → DBC pool + config address)
        ▼
Solana mainnet: DBC config + pool accounts, decoded with the official SDK (100 per call)
        ▼
rules.ts (frozen definitions) ──► analyze.ts ──► data/evidence*.json ──► site, CLI, README numbers
```

| File | Role |
|---|---|
| `collect.ts` | Snapshot the DAMM v2 API, look up each token's DBC config, decode configs on-chain |
| `rules.ts` | The frozen definitions: settings, spam, families, preset rules, warning signs |
| `analyze.ts` | Evidence tables per sample (`RESULTS*.md`, `data/evidence*.json`) |
| `checker.ts` / `resolve.ts` | Verdict for one config; resolve any address to its decoded config (Node and browser) |
| `presets.ts` | Build presets with the SDK's `buildCurve`, validate with `validateConfigParameters` |
| `simulate.ts` | Simulate `createConfig` for each preset against the mainnet DBC program (nothing is sent) |
| `devnet.ts` | Optional devnet launch of a preset (needs devnet SOL) |
| `site/` | Static site; `npx tsx build-site.ts` bundles it |
| `test/` | `npx tsx --test test/*.test.ts` |

## How we checked ourselves

- **Rules before results.** Definitions were written in DATA_NOTE.md before any outcome was read; every
  later change is logged there with its reason and its effect on the numbers.
- **Holdout and confirmation samples.** Preset and warning rules were picked on the Discovery sample, frozen,
  then measured on samples nobody had looked at.
- **Two lookup methods agree.** Configs found through Meteora's DBC API were compared with direct
  `getProgramAccounts` lookups on the same 40 launches: 40 of 40 matched.
- **The chain accepts the presets.** `simulate.ts` sends each preset's `createConfig` to mainnet as a
  simulation: both succeed, and a control that reuses an existing config address is rejected.
- **Tests.** Settings parsing on a real mainnet config, every warning path, preset validity, and both
  negative controls.

## What broke and how it was fixed

- **"60–100 SOL works best" was the launchpad, not the setting.** bags.fun launches all use that band and
  survive far more often. Fix: compare settings only within self-serve launches; show the launchpad table.
- **Rules designed after looking at survivors can fool you.** Fix: freeze them and re-test on untouched
  samples. The anti-sniper preset did not have enough matching launches in the holdout to confirm, and is
  labelled "promising, not confirmed".
- **USDC-quoted curves were read as SOL.** Their DAMM v2 pool paired with SOL, but the bonding curve was
  quoted in USDC (6 decimals), so thresholds were wrong. A unit test on a real config caught it; they are
  now excluded by the config's own `quoteMint`.
- **A stale collector process kept appending duplicate rows.** Found by checking row count against unique
  pools; fixed by killing it by process ID and rebuilding the file.
- **Public RPC throttles `getProgramAccounts`** (about 3 launches a minute). Fix: Meteora's DBC data API
  for the lookup, then batch-decode 100 accounts per call.

## Limits

Only graduated launches are visible here, so this measures how graduates fare, not which settings
graduate. "Alive" is one snapshot. Associations, not causes. SOL-quoted launches only.

Read-only: this project never asks for a wallet, never launches tokens on mainnet and never moves funds.
Historical evidence, not financial advice.
